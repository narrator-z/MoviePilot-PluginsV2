## ChineseSubFinder 插件（字幕守卫）— 新建 + 修复「调用 API 失败」

**需求**：根据 jxxghp/MoviePilot-Plugins 的 chinesesubfinder 插件 + morningstar-ski/chinesesubfinder-optimization（CSF 应用本体，Go 项目，非 MoviePilot 插件），新增一个 ChineseSubFinder 插件，解决官方插件一直报错「调用ChineseSubFinder API失败！」。

**根因定位（核对 CSF 源码）**：
- 路由：`router.Group("/api/v1").Use(middle.CheckApiAuth())`，add-job 路径 `POST /api/v1/add-job`（与官方插件一致，路径没错）。
- 认证：`CheckApiAuth()` 读 `Authorization: Bearer <token>`，比对 `common.GetApiToken()`——即 CSF 设置里的**外部 API Token**，**不是** Web 登录密码/访问令牌。`middle.CheckAuth()`（WebUI 用）比对的是 `common.GetAccessToken()`，两者不同。
- 关键：add-job handler 在所有成功/业务分支都返回 HTTP 200（含 "physical video file not found"）。所以 `status != 200` 只可能来自 401（Token 缺失/不匹配）或 404（路径错）。官方插件在 `!=200` 时只打「调用ChineseSubFinder API失败！」无原因 → 用户无从排查。
- 官方插件另有两处隐患：`@lru_cache` 缓存了 None 结果导致失败后永不重试；蓝光分支 `"%s.mp4" % item_dest / item_dest.name` 会触发 TypeError。

**交付物**：
- `plugins.v2/chinesesubfinder/__init__.py`（v1.0.0，子类 `_PluginBase`，目录名=类名小写）。
- `icons/chinesesubfinder.png`：从优化版仓库 `logo/logo.PNG` 下载的 CSF logo。
- `package.v2.json`：新增 ChineseSubFinder 条目（icon chinesesubfinder.png，version 1.0.0）。
- `README.md`：新增 ChineseSubFinder 文档段。

**改进点**：
- 提供「测试连接」按钮（`get_api` 暴露 `/test` → `__test_connection`）：先 `GET /system-status` 验可达性，再 `GET /api/v1/job-status?job_id=__mp_test__` 验 Token（200=成功，401=失败并带回 message）。`RequestUtils.get()` 返回字符串而非 Response，故测试用 `get_res()`。
- 调用失败记录 HTTP 状态码 + CSF 返回的 message（AccessToken Error / api_key_enabled == false / physical video file not found），并可选通过通知推送。
- 修复蓝光表达式错误；移除失败缓存（不再 lru_cache）。
- 配置表单增加醒目提示：API Token 填 CSF 外部 API Token，非 Web 密码。

**验证**：`py_compile` 通过；`package.v2.json` JSON 校验通过；`.workbuddy/_selftest_csf.py`（stub 全部依赖）覆盖 host 归一化、请求体字段与路径映射、连接测试成功/401、文件不存在分支，**ALL CSF TESTS PASSED**。

## 用户报障：插件市场「添加我的仓库 URL 后搜不到，一个也看不到，其他仓库正常」

**已逐行核对 MoviePilot v2.15.7 市场加载链路（app/helper/plugin.py + app/core/plugin.py），结论：仓库文件没问题，是用户 MP 端拉取失败。**

- `_base_url = "https://raw.githubusercontent.com/{user}/{repo}/main/"`（硬编码 main）。
- `get_plugins` 走 `__request_with_fallback`：优先 `settings.GITHUB_PROXY`（镜像，非 API 请求时）→ `settings.PROXY_HOST`（代理）→ 直连。
- `__parse_plugin_index_response` 只要求 `dict`，我的 package.v2.json 合法（4 个插件）。
- V2 路径（`package_version="v2"`）**跳过** `_process_plugin_info` 里的版本兼容门（`if not package_version` 才校验），所以我的 4 个 V2 插件不会被丢弃；`_process_plugin_info` 也无抛异常风险（annotate 只补字段）。
- 实测 raw URL：`main/package.v2.json` 返回 4 个插件；`package.json`（V1 索引）为空 `{}`（纯 V2 仓库正常态）。

**诊断**：用户设了 GITHUB_PROXY/镜像 → 镜像能服务热门仓库（已缓存），但对我的仓库（较新/不热门）返回 404/空/错误页 → `get_plugins` 返回 None/{} → 我的仓库整列 0。与 jxxghp 官方库能拉到不冲突。

**关键提醒（给用户）**：MP 对 raw 拉取有 1800s 缓存，普通「刷新」不重拉，必须强制刷新才会真正重新请求；且失败原因会写在 MP 日志（`获取v2插件库失败` + 仓库 URL/HTTP 码）。

**补充（用户称"无报错、其他仓库正常、仅此仓库取不到")**：
- 字节级复查：本地与远程 `package.v2.json` 均无 UTF-8/UTF-16 BOM、无非法控制字符、JSON 合法、远程 200 返回 4 个插件 → 仓库内容侧 100% 正常。
- 代码机制匹配：MoviePilot `get_plugins` 在 `res.status_code == 404` 时返回 `{}`（空，不报错）；仅 `None`（网络全失败）才打 `获取...插件库失败` warning。**"无报错却 0 个" 最匹配 404 路径**。
- 404 只发生在用户 MP 服务器→GitHub 的请求被代理/镜像挡掉。其他仓库正常说明全局网络未断，而是**镜像对该小众仓库返回 404**（镜像只同步热门官方库）。
- 给用户可执行定性诊断：在 MP 容器里 `curl -sS -o /dev/null -w "%{http_code}" https://raw.githubusercontent.com/narrator-z/MoviePilot-PluginsV2/main/package.v2.json`；200=MP缓存/设置问题，404/000=服务器侧代理/镜像问题。修复=临时清空 GITHUB_PROXY/MIRROR 强制刷新；若只能用代理且代理不服务小仓库，则改用「本地插件」目录方式（不经 GitHub 网络）。

**我能做的**：仓库侧无法改（数据是好的）。让用户查 MP 日志那条失败记录、或临时清空 GITHUB_PROXY 强制刷新来确认；必要时让他贴代理设置/日志。

## 继续深挖（对比 thsrite + 读全链路代码，定位决定性机制）

用户坚持"改之前能、改之后不能、只有你的仓库取不到"，要求对比 https://github.com/thsrite/MoviePilot-Plugins。本次逐一核实：

1. **thsrite 仓库对照**：其 `package.v2.json` 字段集合 = `author, description, history, icon, labels, level, name, version`，**无 `v2` 字段、无 `system_version`**——与我的字段集合**完全一致**，且 thsrite 能正常加载。→ 证明"缺 `v2`/`system_version` 字段"不是原因。
2. **`get_repo_info`**（helper/plugin.py 603）：对 `https://github.com/narrator-z/MoviePilot-PluginsV2/` 解析为 `user=narrator-z, repo=MoviePilot-PluginsV2`，**解析正确**，非 URL 问题。
3. **`_base_url`**（helper/plugin.py 53）= `https://raw.githubusercontent.com/{user}/{repo}/main/`，硬编码 main；我的默认分支正是 main ✓。
4. **`__request_with_fallback`**（helper/plugin.py 1642）：策略顺序 = **镜像站(GITHUB_PROXY) → 代理(PROXY_HOST) → 直连**。致命点：**第 1675 行 `return res` 对任何 Response 立即返回，哪怕 404 也不往下走直连**。即镜像若返回 404，MP 拿到 404 就停。
5. **`get_plugins` 404 分支**（helper/plugin.py 509）：`if res.status_code == 404: return {}`——**静默空列表、无 warning**；仅 `None`（全失败）才打 `获取...插件库失败`。用户"无报错却 0 个"精确命中 404 路径。
6. **`_process_plugin_info`**（core/plugin.py 1592）：v2 路径（`package_version` 非空）**跳过** `if not package_version` 的版本门；对缺字段不丢弃；`__set_and_check_auth_level` 恒 True。→ 我的 4 个条目不会被代码过滤掉。
7. **`process_plugins_list`**（core/plugin.py 1542）：仅去重/合并/取最高版本，不丢弃合法条目。

**决定性结论**：仓库数据/格式 100% 合规（已对比 thsrite、jxxghp、改动前原版三套）。"无报错、0 个、仅此仓库"唯一代码路径 = 服务器侧拉取 `…/main/package.v2.json` 拿到 **HTTP 404** → `get_plugins` 返回 `{}`。404 来自用户**配置的 GitHub 镜像站(GITHUB_PROXY)**：该类镜像服务热门官方库（已缓存、返回 200），但对我的新/小众仓库返回 404（且 ghproxy 类镜像会**缓存 404**，首次拉取时若仓库文件未齐/瞬时异常即被永久缓存 404）。这正好解释"改之前可以、改之后不行"——我的某次推送瞬间被镜像抓到 404 并缓存。
