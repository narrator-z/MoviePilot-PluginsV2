**决定性主因（13:xx 续 — 这才是"还是返回没有数据"的真正原因）**：

- 调用链实证（`GET /api/v1/search/title` → `search_by_title` → `async_search_by_title` → `__async_search_all_sites` → `async_search_torrents` → `async_run_module("async_search_torrents")` → `__async_execute_plugin_modules`）。
- 插件 `get_module()` 仅返回 `{"search_torrents": self.search_torrents}`。异步分发按方法名 `"async_search_torrents"` 在 `module_dict` 中查找 → 落空 → 插件劫持**永不触发** → 退化为系统 `IndexerModule.search_torrents` 用 torznab **不带 apikey** 直查 → 永远空。这解释了"此前无论怎么修 cat/大小写，UI 搜索仍为空"：因为插件根本没被调用。
- 同步链路（`search_all_sites` → `executor.submit(self.search_torrents)` → `run_module("search_torrents")`）才会命中插件，但 UI 搜索不走这条。

**修复（1.4.2 增量，未升版本号）**：
- `get_module()` 增加 `"async_search_torrents": self.search_torrents`（复用同一同步实现；引擎在异步路径用线程池执行 `run_in_threadpool`）。同步/异步两条链路现在都能命中插件劫持。

**定位（读 NAS 日志实证）**：

## StuckDownloadGuard 插件（下载守卫）— 新建 + 逻辑自测

**需求**：监控下载管理模块下载任务，进度≈0 且速度=0（**不含排队时间**）持续半小时则降级排至队尾；连续多次无效则停止种子、清理下载任务、重新搜索下载（订阅来源）。

**交付物**：
- `plugins.v2/stuckdownloadguard/__init__.py`：子类 `_PluginBase`，目录名=类名小写=插件 ID。
- `package.v2.json`：新增 `StuckDownloadGuard` 条目（version 1.0.0 / author narrator-z / icon Qbittorrent_A.png，图标已确认存在于 `icons/`），与 `plugin_*` 属性保持一致。
- `README.md`：新增 StuckDownloadGuard 文档段（按 JackettExtend/ProwlarrExtend 同格式）。

**关键设计**：
- 为区分「排队中」与「下载中」，直接调用下载器原生客户端（`qbittorrentapi.Client` / `transmission_rpc.Client`）读原始状态——MoviePilot 的 `DownloadChain.list_torrents` 把 `queueddl` 归一化为 DOWNLOADING，无法区分。
- 仅处理带 `settings.TORRENT_TAG`（MOVIEPILOT）标签的种子。
- 每 hash 持久化状态机 `{active_stuck, last_ts, retries}`：stuck 时按 `now-last_ts` 累加（排除队列时间，队列只置 `last_ts=None` 暂停、不累加）；达 `inactive_minutes`（默认30）触发 `__handle_stuck`：retries<max_retries(默认3) → 降级+重置计时；否则 → 升级（停止+清理+经 `SubscribeChain.get_subscribe_by_source`→`search` 后台线程重新搜索，非订阅来源仅止损）。
- 健壮性：用 `SystemConfigOper().get(SystemConfigKey.Downloaders)` 取下载器配置（规避本地 checkout 中已重命名的 `DownloadHelper`）；`SubscribeChain` 导入 `try/except` 兜底。
- 升级处理后 `pop` 该 hash 记录，避免下一轮重复升级。

**自测**：`.workbuddy/_selftest_stuck.py`（stub 全部 MoviePilot 依赖 + 可变时钟），覆盖 classify_state、Scenario A（30min 降级）、B（再 30min 升级 stop+remove+research 并清空记录）、C（排队时间不计入）。**ALL TESTS PASSED**。
- 自测中修复的真实 bug：升级处理后未 `pop` 记录 → 同一任务每轮重复升级。已在 `monitor→__handle_stuck` 的 else 分支 `self._states.pop(hash_str, None)` 修复。
